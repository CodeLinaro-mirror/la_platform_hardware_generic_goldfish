# Emulator Crash Report Tool

This directory contains the `crashreport` tool, which is used to manage, upload, and analyze crash reports generated by the Android Emulator.

As an emulator developer, you can use this tool to inspect crashes that occur during development runs, especially when running the emulator within the Bazel environment.

## Quick Start

When running the emulator using Bazel:
```bash
bazel run @goldfish//emulator/launcher:launch_emulator -- <emulator_args>
```
If the emulator crashes, a minidump will be written to the local crash database.

You can then run the `bazel_crashreport` wrapper to analyze the crash:
```bash
bazel run @goldfish//emulator/crashreport/tool:bazel_crashreport -- --minidump latest
```
This wrapper automatically packages, extracts, and configures the necessary symbol files from the build, allowing the underlying tool to produce a fully symbolized stack trace.

## Common Commands

The Bazel wrapper accepts the exact same arguments as the underlying C++ `crashreport` binary and forwards them directly.

### 1. List crash reports in the database
Shows all crash reports, their status (pending/uploaded), and remote report IDs if available.
```bash
bazel run @goldfish//emulator/crashreport/tool:bazel_crashreport -- --list
```

### 2. Analyze the latest crash
Parses the latest minidump in the database and prints a symbolized stack trace.
```bash
bazel run @goldfish//emulator/crashreport/tool:bazel_crashreport -- --minidump latest
```

### 3. Analyze a specific minidump file (Standalone)
If you have a raw `.dmp` file (e.g., shared by someone else), you can analyze it directly without using the database.
```bash
bazel run @goldfish//emulator/crashreport/tool:bazel_crashreport -- --minidump /path/to/crashed.dmp --standalone
```

### 4. Upload pending reports
Attempts to upload all pending crash reports to the staging crash server immediately.
```bash
bazel run @goldfish//emulator/crashreport/tool:bazel_crashreport -- --upload
```
*Note: If the upload succeeds, the remote report ID will be stored in the database. You can retrieve it by running `--list` again. This ID can be shared in bug reports.*

### 5. Erase all reports
Cleans up the database by deleting all local crash reports.
```bash
bazel run @goldfish//emulator/crashreport/tool:bazel_crashreport -- --erase
```

### 6. Extract only breadcrumbs (Skip stack walk)
If you only need to analyze the breadcrumb events (gRPC/ADB) and don't need the stack trace, you can skip the stack walking process. This is faster as it avoids processing stack traces for all threads.
```bash
bazel run @goldfish//emulator/crashreport/tool:bazel_crashreport -- --minidump latest --content=breadcrumbs
```

## How Symbols Work

The Bazel wrapper (`bazel_crashreport`) has a dependency on `//emulator:package_goldfish_symbols_extract`.
When you run the wrapper with `--minidump`, it:
1. Locates all `.sym` files generated during the build.
2. Extracts and structures them in a temporary directory matching the Breakpad symbol path format (`<module_name>/<debug_id>/<module_name>.sym`).
3. Passes this temporary directory to the C++ tool via the `--symbol_paths` flag.

This is done transparently under the hood. You do not need to specify `--symbol_paths` unless you want to include additional, custom symbol directories (which will be merged with the build symbols).

## Advanced: Post-processing Crashes from go/crash (Production/External Runs)

If you need to analyze a crash that occurred outside your local environment (e.g., from a user report on `go/crash`), you can download the minidump and post-process it locally with the correct symbols.

> [!NOTE]
> For official release builds, symbols are automatically uploaded to the crash server during the CI build process (see [build.py](file:///usr/local/google/home/jansene/src/emu-main-next/tools/buildSrc/servers/build.py)). This allows `go/crash` to symbolize reports automatically. However, local post-processing is still required if you need to extract and analyze breadcrumbs, or if you are debugging a local/unofficial build where symbols were not uploaded.

### Step 1: Download the Minidump
Go to the crash report on `go/crash` and download the raw minidump file (usually has a `.dmp` extension, e.g., `crash_123456789.dmp`).

### Step 2: Download the Matching Symbols
To get a useful stack trace, you need the symbols that match the exact build of the emulator that crashed.
1. Identify the **Build ID** from the crash report on `go/crash` (or the emulator version string).
2. Go to Android Build: `go/ab`.
3. Search for the build ID.
4. Locate the emulator build target for the relevant platform (e.g., `emulator-linux`, `emulator-mac-arm`).
5. Under **Artifacts**, find and download the breakpad symbols zip. The filename will look like:
   `sdk-repo-[linux|darwin_aarch64|windows]-emulator-debug-breakpad-symbols-[buildid].zip`
6. Extract the zip file to a local directory:
   ```bash
   unzip sdk-repo-linux-emulator-debug-breakpad-symbols-1234567.zip -d /tmp/symbols
   ```

### Step 3: Run the Tool in Standalone Mode
Execute the `bazel_crashreport` tool, pointing it to the downloaded minidump and the extracted symbols:
```bash
bazel run @goldfish//emulator/crashreport/tool:bazel_crashreport -- \
    --minidump /path/to/crash_123456789.dmp \
    --standalone \
    --symbol_paths /tmp/symbols
```
This will print the symbolized stack trace for the crash.

## Breadcrumbs Analysis

The `crashreport` tool automatically extracts and visualizes breadcrumbs (if present in the minidump). Breadcrumbs record recent internal events (like gRPC calls or ADB commands) leading up to the crash, which is invaluable for debugging concurrency or state issues.

Currently, the tool supports:
* **gRPC Breadcrumbs**: Records internal gRPC traffic.
* **ADB Breadcrumbs**: Records ADB commands processed by the emulator.

### Formatting Breadcrumbs
By default, breadcrumbs are rendered as a text timeline. You can change the format to render a sequence diagram:

* **Text Format (Default)**:
  ```bash
  bazel run @goldfish//emulator/crashreport/tool:bazel_crashreport -- --minidump latest
  ```
* **Mermaid Format**:
  Generates a Mermaid JS sequence diagram that you can paste into markdown viewers (like GitHub/Gerrit) to visualize the call flow.
  ```bash
  bazel run @goldfish//emulator/crashreport/tool:bazel_crashreport -- \
      --minidump latest \
      --breadcrumb_format mermaid
  ```

### Interpreting Breadcrumbs
The breadcrumb trace shows:
* **Timestamps** of events.
* **Thread IDs** associated with each event. The thread that actually crashed will be highlighted in the output (if it can be identified).
* **Call Details**: For gRPC, it shows the method called, request/response details, and status.
