# Component: virtio-gpu-gfxstream Device

**Role:** The emulator's 3D graphics card. A QEMU `VirtIOGPU` subclass that forwards virtio-gpu commands to [gfxstream](https://android.googlesource.com/platform/hardware/google/gfxstream/) through its `stream_renderer_*` C API, and keeps gfxstream's state in sync with QEMU's snapshots. It is the successor of QEMU's in-tree `virtio-gpu-rutabaga` (same guest-visible device, no rutabaga_gfx layer): `virtio_gpu_gfxstream.c` is a near-verbatim copy of `third_party/qemu/hw/display/virtio-gpu-rutabaga.c` (`diff -u` against it to review), kept close on purpose so fixes can be ported in either direction; during the side-by-side period the launcher instantiates exactly one of the two, selected with the `-virtio-gpu-device rutabaga|gfxstream` launcher option (default `rutabaga`, see `launcher/launch_qemu/virtio_gpu_selection.h`).
**Location:** `hardware/generic/goldfish/emulator/plugin/hal/virtio_gpu_gfxstream`
**Namespace:** `TYPE_VIRTIO_GPU_GFXSTREAM` (QOM: `virtio-gpu-gfxstream-device`, `virtio-gpu-gfxstream-pci`)

## Integration Guide
| Class / Interface | Bazel Target | Header Path | Description |
| :--- | :--- | :--- | :--- |
| `virtio_gpu_gfxstream_register_types` | `:virtio_gpu_gfxstream` | `include/goldfish/devices/virtio_gpu_gfxstream/virtio_gpu_gfxstream.h` | QEMU type registration; called from `plugin.cc` `GF_REGISTER_TYPES_FUNC`. |
| `virtioGpuGlueGetInstance`, `virtioGpuGlueImageRead`, `virtioGpuGlueImageTransfer` | `:virtio_gpu_glue` | `include/goldfish/devices/virtio_gpu_gfxstream/virtio_gpu_glue.h` | Host-side read-back / upload of a guest virtio-gpu resource (multi-display, camera gralloc); finds whichever of `virtio-gpu-gfxstream` / `virtio-gpu-rutabaga` exists through QOM and calls the matching renderer API (the rutabaga path through `@qemu//google/rutabaga:rutabaga_ffi_lazy`). |
| `gfxstream_*` (`gfxstream_init`, `gfxstream_resource_create_3d`, ...) | `:gfxstream_renderer` (private) | `gfxstream_renderer.h` | The `rutabaga_*` FFI shape (`struct gfxstream_builder`, `_transfer`, `_fence`, ...) implemented 1:1 on the `stream_renderer_*` table, plus the few behaviours rutabaga_core used to add (capset index table, default context name, `cmd_size % 4`, empty-box short-cut, ring 1 fences, `<dir>/gfxstream/` snapshot sub-directory). This is what lets the device file stay a rename of QEMU's. |
| `gfxstream_backend_load` | `:gfxstream_backend_loader` (private) | `gfxstream_backend_loader.h` | Opens `libgfxstream_backend` via GLib `GModule` (`G_MODULE_BIND_LOCAL`, thread-safe via `g_once_init_enter` / `g_once_init_leave`) and resolves the `stream_renderer_*` function table; called from `gfxstream_init()`. |

The launcher (`//emulator/launcher/launch_qemu:gpu_device`) instantiates it (with `-virtio-gpu-device gfxstream`) as
`-device virtio-gpu-gfxstream,id=...,hostmem=4096M,gfxstream-vulkan=on[,x-gfxstream-gles=on],x-gfxstream-composer=on,renderer_features=...,snapshot_directory=...,xres=...,yres=...[,wsi=headless][,edid=off,max_outputs=2]`.
QEMU's `system/qdev-monitor.c` aliases `virtio-gpu-gfxstream` to the `-pci` / `-device` type for the bus in use.

### Properties
| Property | Effect |
| :--- | :--- |
| `gfxstream-vulkan`, `x-gfxstream-gles`, `x-gfxstream-composer` | Enable capsets 3 / 8 / 9 (reported to the guest in that order) and the matching `STREAM_RENDERER_FLAGS_USE_{VK,GLES}_BIT`. At least one is required: `realize()` fails with "no capset enabled" where `virtio-gpu-rutabaga` would have fallen back to a 2D-only device (the launcher always passes `gfxstream-vulkan=on`). `cross-domain` / `wayland-socket-path` do not exist. |
| `renderer_features` | Passed verbatim as `STREAM_RENDERER_PARAM_RENDERER_FEATURES`. |
| `wsi` | `surfaceless` (default) reads scanouts back into pixman surfaces for the QEMU console; `headless` skips all scanout work. |
| `snapshot_directory` | Root under which `<snapshot name>/renderer/gfxstream/` holds gfxstream's snapshot files (same layout as `virtio-gpu-rutabaga`, minus its `rutabaga_snapshot` JSON). |
| `x-verify-state` | `off` / `log` (default) / `enforce` / `strict`: what to do when a device invariant check fails around reset, save and load. |
| `hostmem`, `max_outputs`, `xres`, `yres`, `edid` | Inherited from `virtio-gpu-device` / `virtio-gpu-base`. |

## Critical Infrastructure
* **Lazy backend loading.** Neither `qemu-system-*` nor `libgoldfish_*` links `libgfxstream_backend`. `realize()` calls `gfxstream_init()`, which calls `gfxstream_backend_load()`: it looks for the library in `$ANDROID_EMULATOR_LIBRARY_DIR` (set by the launcher to `<emulator>/lib/qemu`), then next to the plugin itself, and only when the variable is unset on the loader's default path (so a packaged emulator never silently picks up a foreign copy); it fails `realize()` with the loader's error text (missing file, `dlerror()`, missing symbols) if it cannot be used. The library is never unloaded. Emulators that do not instantiate the device never map EGL/ANGLE/Vulkan through it: `-gpu off`, and the launcher's default `virtio-gpu-rutabaga`, whose `librutabaga_ffi` embeds its own copy of gfxstream (the two copies must not coexist in one process, hence QEMU's lazy `rutabaga_ffi_lazy` shim as well).
* **Command path.** `process_cmd` is QEMU's rutabaga one; each `gfxstream_*` call is one `stream_renderer_*` call. The only additions over the QEMU file are the id checks rutabaga_core used to make (duplicate resource/context ids on create; unknown context on `SUBMIT_3D`, `CTX_DESTROY`, blob create and ring fences; unknown context or resource on `CTX_ATTACH/DETACH_RESOURCE`; gfxstream silently overwrites or ignores unknown table entries), a `nlen` clamp on `CTX_CREATE`, `SUBMIT_3D` sizes that are not a multiple of 4, and empty transfers short-circuited inside `gfxstream_resource_transfer_*`.
* **Host memory BAR.** `MAP_BLOB` maps the blob with `stream_renderer_resource_map()` and inserts a `MemoryRegion` into the `hostmem` BAR in one of `MAX_SLOTS` (4096, from `hw/virtio/virtio-gpu.h`) slots, hashed by resource id. The slot table is serialized as the `virtio-gpu-gfxstream/slots` VMState subsection and re-mapped in `post_load`.
* **Fences.** gfxstream signals fences either synchronously inside `stream_renderer_create_fence()` or from its own render/sync threads. The callback only pushes onto a lock-free `QSLIST` and schedules a BH; the BH retires matching entries of `g->fenceq` with the BQL held. Fences on `ring_idx == 1` are completed immediately without involving gfxstream (gfxstream never queues work on that ring).
* **Snapshots.** VMState `virtio-gpu-gfxstream` version 3 follows the `virtio-gpu-rutabaga` v3 stream structure under its own section name (with 64-bit `blob_size` and `iov_len` fields so >= 4 GiB blobs do not truncate): contexts, resources, in-flight fenced commands, the pixels of every console surface, the scanout table and the `virtio-gpu-gfxstream/slots` subsection. The renderer itself is saved with `stream_renderer_snapshot()` into a staging directory that is renamed over `<snapshot_directory>/<snapshot name>/renderer/`, with the files in its `gfxstream/` sub-directory (`gfxstream_renderer.bin`, `gfxstream_frontend.txtproto`, `gfxstream_asg.bin`); the snapshot name comes from `qemu_snapshot_in_flight_name()`. `pre_load` tears down every guest object (re-initializing gfxstream if a previous restore never completed), `load` calls `stream_renderer_restore()` before parsing the stream, and `post_load` re-attaches guest backing, re-maps BAR slots, rebuilds scanout surfaces and completes restored fences. Context/resource attachments are not replayed: gfxstream restores them from its txtproto. Because the VM state section is named differently from `virtio-gpu-rutabaga`, the selected device is encoded in the snapshot version (`SnapshotGpuDevice`, bits 15..14, `libs/snapshot`), so a snapshot saved with the other device is cold-booted with a logged reason instead of failing mid-load.
* **Reset / wait-for-idle.** On `SAVE_VM`, `PAUSED`, `FINISH_MIGRATE` and `SHUTDOWN` the VM-state-change hook drains `ctrl_vq` and polls until every fence has been retired (5 s timeout). `reset` unmaps BAR slots, resets the parent device, frees contexts and re-initializes gfxstream (`stream_renderer_teardown()` + `stream_renderer_init()`) if it was in use.
* **Windows portability.** `Property` and `VMStateField` tables reference QEMU data symbols from another binary, so they are filled in at runtime by `virtio_gpu_gfxstream_init_tables()` from `virtio_gpu_gfxstream_register_types()` (same pattern as `//emulator/plugin/battery`). QEMU trace points are compiled out and `VIRTIO_GPU_FILL_CMD` reports through `error_report()` because the trace/log state is not exported either.
* **Invariant checker.** `x-verify-state` runs the `gfxstream_verify_*` checks (queues/fences, context and resource tables, slot table, scanouts, on-disk snapshot completeness) before/after reset, wait-for-idle, save and load; `info virtio-gpu-gfxstream` (HMP) prints a summary.

## Dependencies
* **QEMU:** `@qemu//:qemu-headers-exported`; the `virtio_gpu_*`, `virtio_gpu_base_*`, `qemu_*_virtqueue_element`, `qemu_snapshot_in_flight_name`, `monitor_*`, `aio_poll`, `qemu_console_is_visible`, `qemu_create_displaysurface_from` and `object_class_property_add_enum` symbols are exported by `third_party/qemu/google/build/qemu-system-*.def`.
* **gfxstream:** headers only (`third_party/gfxstream/`, vendored; see its README), used by `gfxstream_renderer.c` and the loader; `libgfxstream_backend` is packaged into `lib/qemu` by `//emulator:plugin_binaries` and `//emulator/launcher:plugins`.
* **pixman:** `@pixman//:pixman-1` for scanout surfaces.

## Threading Model
* **QEMU main thread (BQL):** everything except the fence callback: command processing, snapshots, reset, `virtioGpuGlueImage*` callers.
* **gfxstream threads:** `virtio_gpu_gfxstream_fence_cb()` and `virtio_gpu_gfxstream_debug_cb_ex()` may run on gfxstream's render / sync threads; they only touch the atomic fence list, the BH and `error_report()`.
* `virtioGpuGlueImageRead` / `virtioGpuGlueImageTransfer` call straight into the renderer, whose resource table is not locked against the command path: callers must hold the BQL.
